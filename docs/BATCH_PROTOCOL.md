# EasyVoca｜24チャット並列調査プロトコル v3

## 範囲と実行方法
同じ共通プロンプトの**最後に独立した1行で1〜24の番号を付けるだけ**で担当バッチを指定する。番号Bの担当は `(B-1)*500+1`〜`B*500`（両端含む）。例：1→1〜500、2→501〜1000、24→11501〜12000。

各担当は**第1段階：候補選定 → 第2段階：裏付け・採否確定**を行う。コアイメージ・完成例文・学習アプリは作らない。

## 必須前提：12,000語固定マスター
- `data/master/words.jsonl` が存在し、`index`（1〜12000、連続・重複なし）・`word`・`level`・`source` を持つこと。出典・ライセンス・バージョンを固定する。
- 2026-11-22に**生成・検証済み**。確定版のSHA-256および出典情報は `data/master/manifest.json` を参照。24バッチの範囲は `data/master/batches.json` に固定する。
- `index` はEasyVoca内の管理番号であり、SVL12000の単語リスト・公式順位ではない。Lingevo/OANCの見出し語頻度を基礎にLexiCore-5000で学習語を補完したEasyVoca独自の索引。levelは便宜上の1,000語刻みであり、CEFRや入試難易度を保証しない。公開条件とクレジットは `docs/SOURCE_CREDITS.md` に記録。
- マスターが見つからない、担当番号の500件が抽出できない、マスターのハッシュがmanifestと違う場合は、語を推測・捏造して補充せず、阻害要因を報告する。24担当はマスターを編集しない。

## ファイルと判定
各バッチは**自分の専用ファイル**のみを編集する。たとえば1番なら：
- `data/review/batch_00001_00500.jsonl`：500単語に1行ずつ。進捗・候補件数・採用件数。
- `data/candidates/batch_00001_00500.jsonl`：第1段階で見つけた候補を語義ごとに1行。第2段階の採否理由と出典も同じ行に保存する。
- `reports/batch_00001_00500.md`：作業概要、対象語数、調査済み数、採用／除外／要確認件数、資料、未完了の理由、PR・コミット。

調査行の例：
```json
{"index":1,"word":"snake","status":"verified_selected","candidate_count":1,"accepted_count":1}
```
*これはフィールド形式の例であり、実際のマスター番号1がsnakeとは限らない。*

語単位の `status`：
- `verified_selected`：調査完了、少なくとも1件の採用確定あり
- `verified_none`：調査完了、採用確定は0件（検討したが不採用も含む）
- `needs_review`：途中・根拠不足・採否未確定

候補行の例：
```json
{"candidate_id":"ev-00001-verb-01","index":1,"word":"snake","pos":"verb","meaning_ja":"蛇行する","reason":"基本名詞から別品詞の意味を見落としやすい","utility":"道の形状などの英文を読むのに役立つ","decision":"accepted","decision_reason":"辞書の動詞用法に合致し、読解で実用的","sources":[{"name":"Wiktionary","url":"https://en.wiktionary.org/wiki/snake","checked_at":"2026-11-22"}]}
```
*形式の例。出典の確認・採否をこの例で証明するものではない。*

候補 `decision` は `accepted`、`rejected`、`needs_review` のいずれか。情報源を確認できない候補は `accepted` としない。候補・語義は独自の簡潔な日本語で記述し、辞書本文を複製しない。

## 作業手順
1. 固定マスター・基準・ライセンス・対象500語を確認。
2. 500語について各種辞書の品詞・別義・用法を調べ、見落としやすく実用的な候補を抽出。検討後に候補0件でもよい。
3. 候補について出典を確認し、`accepted` / `rejected` / `needs_review` を根拠付きで記録。
4. 担当専用の `selection/00001-00500` 等のブランチで進捗を随時コミットし、main向けPRを作成。複数回の実装・検証・コミットを行ってよい。途中ならDraft PR。
5. 500語の各番号がレビュー行に1回ずつ現れ、対応する語・候補数・採用数が一致し、出典不足・未検証が紛れ込んでいないことを検査する。
6. 全員完了後に24バッチ横断の重複・整合性検査を行う。別担当のファイル・共通仕様を編集しない。

## 完了判定
「500語について第1〜2段階が完了」と報告するには500語すべての調査と各候補の採否確認が終わり、`needs_review` が0である必要がある。未調査行を `verified_none` にしない。作業途中では処理済み数と未完了数を正確に報告し、保存した進捗から再開できる状態にする。採用語義数はノルマにしない。
